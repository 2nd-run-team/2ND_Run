# 기획안 1 우주 화물열차 프로토타입 제작 계획서

작성일 2026년 10월 1일 · 초안 v0.1 · 대상 프로젝트 SpacePirate · Unreal Engine 5.8.2

**기획안 1은 객차마다 다른 위험을 읽고, 화물을 더 확보할지 앞칸으로 이동할지 팀이 결정하는 재미를 검증한다.** 기존 열차와 이동 코드를 토대로 일반 화물 자동 전송, 객차 기믹, 제한시간과 탈출을 새로 연결한다. 먼저 6칸에서 한 판을 완성하고, 검증용 본편은 정비 칸을 포함한 고정 10칸으로 확장한다. 절차적 생성과 포드 운반은 본편의 재미를 확인한 다음 별도 실험으로 추가한다.

이 문서는 제작 계획이다. 게임 코드나 원본 맵을 변경한 결과물이 아니며, 아래 설계와 수치는 실제 플레이테스트 전의 제안이다. 자료의 ‘확정’ 표기도 이번 사용자가 허용한 재검토 범위 안에서 판단했다.

## 1 검증할 기획의 범위

| 구분 | 자료에서 읽은 핵심 재미 | 이번 제작과의 관계 |
|---|---|---|
| 기획안 1 요약 PDF | 제한시간, 서로 다른 객차, 자동 전송, 전진과 욕심의 선택 | 이번 프로토타입의 기준 |
| 기획안 2 요약 PPTX | 작업자 위장, 정찰과 보안 해제, 가방 운반과 무중력 선적 | 다음 계획서에서 독립적으로 검증 |
| 기획안 3 요약 PPTX | 사전 작전으로 얻은 정보·장비가 피날레의 동선을 바꿈 | 1·2를 평가한 후 연결 효과를 검증 |
| 객차 컨셉과 화물 확보 PDF | 기획안 1의 구체적인 장치·상호작용 후보 | 필요한 부분을 선택하고 충돌 규칙을 정리 |
| 상세 DOCX 00부터 05 | 기획안 2의 상태, 보안, 운반, 보상, 화면 규칙 | 동시 입력 처리·표현·레벨 검수 원칙만 필요한 만큼 참고 |

기획안 1에 위장, 확률 검문, 체포와 호송, 현금 포장, 탈출선 선적, 세 판의 작전 경제를 넣지 않는다. 이 기능들이 섞이면 어느 기획의 재미가 작동했는지 판단하기 어렵다. 기존의 Large 협동 운반도 일반 화물의 필수 과정으로 쓰지 않는다. 자동 전송으로 운반 동선의 제약을 줄이려는 기획안 1의 취지를 유지한다.

### 검증 가설

1. **선택**: 플레이어가 가치와 위험을 이해하고 눈앞의 화물을 자발적으로 남긴다.
2. **객차 변화**: 다음 객차의 기믹 때문에 이동 경로와 확보 순서가 달라진다.
3. **협동**: 각자 줍기 외에도 문 열기, 위험 타이밍 전달, 합류 요청이 생긴다.
4. **재도전**: 실패 뒤 ‘다음에는 무엇을 다르게 할지’를 말할 수 있고 다시 하려 한다.

단순히 끝까지 달렸거나, 동시 버튼 때문에 대화했다는 사실만으로 가설을 통과시키지 않는다. 그 행동의 이유를 테스트 후 질문한다.

## 2 현재 프로젝트 확인과 재사용 판단

확인 기준은 저장소 `f2a6235`와 작업 시작 당시의 파일이다. 최초 Git 작업 트리는 깨끗했다. `SpacePirate.uproject`의 EngineAssociation은 `5.8`이고, 설치 엔진 `E:/UE_5.8/Engine/Build/Build.version`에서 패치 `5.8.2`, Changelist `56702186`을 확인했다. 실제 모듈 이름은 `SpacePirate`이며, 작업 폴더명 `2ND_Run`이나 이전 모듈 `SecondRun`과 구분해야 한다.

이번 확인에서는 UE 5.8.2의 별도 `UnrealEditor-Cmd`로 기존 열차 검사 스크립트와 읽기 전용 BP 점검을 실행했고 종료 코드 0을 확인했다. **현재 파일 기준 에셋 110개 로드, Blueprint 37개 컴파일, 게임 의존 패키지 285개 검사에서 누락·이전 경로 참조·검사 오류는 0개였다.** 플레이어 BP의 C++ 부모, 입력 에셋 연결, 컨트롤러의 `IMC_SPPlayer`, 화물 BP의 Small/가치 0 기본값, Train GameState의 GameStateBase 부모, 맵의 PlayerStart 4개도 확인했다. 에셋을 저장하지 않았다. 이번에 C++ 전체 리빌드나 PIE 실플레이를 재실행한 것은 아니다.

|---|---|---|
| 1인칭 플레이어 | `Source/SpacePirate/SPPlayerCharacter.*`에 카메라, Enhanced Input, 이동·집기 연결 | 재사용. Prototype01 자식 Pawn과 입력으로 분리 |

| 열차와 배경 | `/Game/SpacePirate/Maps/Lvl_SPTrainFreight`, `Train/Freight`의 편성·차량 5종, `Train/Systems`와 배경 에셋 | 복제 맵에서 재사용. 열차 고정·배경 이동 방식 유지 |

**새로 필요한 핵심 기능**은 유지형 확보와 자동 전송, 팀 가치 원장, 라운드 상태와 서버 타이머, 탈출 정산, 상처·스태미나, 객차 장치, HUD, 테스트 기록이다. 현재 팀 플레이어 코드에 이 한 판의 흐름이 완성되어 있지는 않다. Blueprint 에셋은 존재만으로 게임 규칙까지 구현되었다고 판단하지 않는다.

### 구현 전에 주의할 연결점

- 현재 E 입력은 `Started`에서 즉시 집기를 호출한다. 홀드 확보는 `Started`, `Completed`, `Canceled`를 처리해야 하며, 한 입력으로 즉시 집기와 확보를 함께 실행하면 안 된다.
- 현재 일반 화물 집기는 클라이언트 조준 검사 뒤 서버에서 거리 400cm를 확인한다. 새 확보에서는 서버의 거리·시선·가림 검사를 지속적으로 수행한다. 기존 함수를 그대로 전송 판정에 쓰지 않는다.
- 현재 `ASPCargo`의 Mid는 양손이다. 자료의 N02는 한 손으로 도구 사용이 가능하므로 포드를 Mid로만 설정해서는 요구를 만족하지 않는다.
- 현재 `CargoValue`는 배치/BP 기본값을 전제로 복제하지 않는다. 서버에서 가치를 무작위 결정한다면 결과값이나 데이터 식별자를 복제해야 한다.
- 무중력 영역 밖 기본값은 중력이다. 객차뿐 아니라 연결 통로의 경계, 천장 접촉, 중력 복귀를 확인한다.
- 실제 플레이어 BP 걷기 속도는 400cm/s, 달리기 700cm/s, 무중력 최고속도 700cm/s, 가속도 500cm/s², 항력 0이다. 아래 제안의 걷기 450cm/s는 새 시험값이며, 공용 BP를 덮어쓰지 않고 전용 자식 BP에서 비교한다.
- 기본 시작 맵과 전역 GameMode는 FirstPerson 템플릿에 남아 있다. 새 맵의 World Settings로 전용 GameMode를 지정하고, 프로젝트 전체 시작 설정 변경은 필수로 삼지 않는다.
- 기존 Train GameState에는 열차·하늘 상태가 있다. 새 라운드 GameState로 무심코 교체하면 배경 연결이 끊길 수 있다. 기존 GameState에 라운드 컴포넌트를 부착하는 방식을 우선 검토한다.

## 3 자료의 충돌과 이번 적용 규칙

다음은 원문을 그대로 옮긴 규칙이 아니라 이번 프로토타입의 제작 결정이다.

| 쟁점 | 자료의 차이 또는 위험 | 이번 적용 |
|---|---|---|
| 부활 | 화물 확보 PDF 3.4는 부활 없음, 요약 1의 6장은 정비 칸에서 부활 | 요약 1을 채택. 최종 10칸에서는 정비 중 1회 부활 허용 |
| 종료 직전 탈출 | 확보 PDF 3.3은 카운트다운 시작 후 제한시간 면제, 요약 1은 제한시간 종료 시 실패 | 제한시간을 끝까지 적용. 출발이 시간 만료와 같거나 늦으면 실패 |
| 정비 칸 수 | 10칸 중간에 별도 정비 칸을 삽입하는 예시라 실제 물리 칸 수가 불분명 | **총 10량에 정비 1량과 기관실 1량 포함** |

| 경보 | 추격·공격 또는 20초 확보 금지와 8초 문 봉쇄가 미정 | 최초에는 카메라만 사용. 발각 시 예고 후 상처 20의 국소 방어 펄스. 문 봉쇄·장시간 확보 금지는 제외 |
| 감시 피해 | 로봇 전투를 먼저 만들면 AI 검증이 주요 과제가 됨 | 시야와 노출 판단을 먼저 검증. 로봇 추격은 후속 독립 비교 |
| 정비 시간 정지 | 선두 한 명이 진입하면 후방 팀원이 30초 동안 추가 약탈 가능 | 이 효과를 명시적으로 허용한 시험안. 월드가 아니라 임무 타이머만 멈춤. 정비 중 후방 획득액을 기록 |
| 2인 격벽 | 두 생존자가 필요하면 한 명 사망 후 진행 불가 | 누구나 쓸 수 있는 12초 단독 우회 콘솔 제공. 두 명 2초 협동이 더 빠름 |
| 경고 없음 | 종료를 몰라 실패하면 욕심보다 정보 누락을 평가하게 됨 | 남은 시간 상시 표시, 60초·30초 경고, 탈출 구역 안팎 인원 표시 추가 |
| 마이크 기믹 | 근접 음성·음량 보정·환경 소음까지 필요 | C06·C12와 게임 내 음성은 후순위. 외부 음성+핑으로 핵심 판단 검증 |
| 절차적 생성 | 기믹, 난이도, 배치가 한꺼번에 바뀌면 실패 원인 불명 | 고정 A/B 배치 먼저. 이후 시드와 생성 결과를 기록하는 제한적 생성 |

추가로, 객차 PDF의 EMP 설명은 주기 15·12·10초와 ‘확보 시간 약 7.5초’를 함께 쓰므로 강도별 안전 시간을 별도로 산출해야 한다. 난이도 4 총 가치 범위와 난이도 3 대비 1.6~2배는 범위의 모든 조합에서 성립하지 않는다. 이 두 항목은 이번 범위에 넣지 않고 후속 데이터 검증 대상으로 남긴다.

`화물_종류와_수치_기획서`와 `체력과_피해_기획서` 원본은 첨부에 없다. 요약에 나온 값만 인용하고, 누락된 값은 아래 시험값으로 새로 정했다. 추가 원본이 있는 것처럼 취급하지 않는다.

## 4 제작 범위

### 필수 결과물

- 2인과 4인이 플레이하는 Listen Server 기반 1인칭 프로토타입. 1인은 개발 점검용으로 통과 가능.
- 처음에는 6칸, 최종 검증에는 10칸 고정 편성 한 판과 비교용 배치 B.
- 일반 전송 화물 4종, 중력 교란 화물 S01 한 종류. 외형 변형은 데이터로 처리.
- 객차 다섯 컨셉 C01 장애물, C02 적재, C03 중력 기믹, C04 감시, C09 보안 격벽.
- 상처와 스태미나 한 게이지, 사망과 관전, 정비 칸 1회 이용, 10초 탈출, 결과와 빠른 재시작.
- 필요한 정보를 보여주는 HUD, 대상 핑, 서버 이벤트 로그.
- 선택 도구 1종은 본편 연결 뒤 추가한다. 초기 기믹은 도구가 없어도 통과 가능해야 한다.

### 별도 실험

포드 N01 한 개, 적재 칸 자동 하역 타이머, 감시 로봇, 근접 음성, 제한적 절차 생성은 기본판 합격 뒤 각각 따로 시험한다. 포드의 각성 후 적대 NPC는 그다음 단계다. 포드를 단순 가치 상실로만 시험했으면 ‘괴물로 인한 재미’까지 검증했다고 보고하지 않는다.

기획안 1의 첫 판에 12종 객차 전체, 난이도 4단계, 상점과 성장, 인터넷 매칭, 호스트 이전, 재접속 복구를 만들지 않는다.

## 5 한 판의 규칙

### 시작과 시간

모든 참가자가 준비된 뒤 호스트가 시작한다. 로딩 시간은 임무 시간에 넣지 않는다. 라운드 상태는 `Ready`, `Running`, `ExtractionCountdown`, `Succeeded`, `Failed`, `Aborted`로 구분한다. 정비 활성 여부는 별도 상태이며 플레이어 이동과 위험은 계속 작동한다.

본편 시작값은 **임무 시간 420초**다. 정비에서 최대 30초 멈추므로 실제 진행 시간은 최대 450초다. 탈출 준비 10초는 이 예산 안에서 소비한다. 원안의 600초도 같은 맵에서 비교한다. 420초가 정답이라는 뜻은 아니며, 시간 측정 기준은 10장을 따른다.

### 화물 확보

시점 기준 250cm 안의 보이는 상호작용 지점을 겨냥하고 E를 누른다. 유지 거리 300cm, 시선 허용각 20도, 시선 이탈 유예 0.25초를 시작값으로 사용한다. 거리 경계에는 최대 0.1초 유예를 두되 완료 순간에는 서버의 유효 판정을 통과해야 한다. 벽 너머 확보를 허용하지 않는다.

확보 중 지상 이동속도는 기본 걷기의 50%다. 달리기·점프·도구 사용·슬롯 전환을 차단한다. 무중력에서는 이동을 순간 정지시키지 않고 추진 입력을 제한한다. 관성으로 유지 범위를 벗어날 수 있어 자세를 먼저 안정시키는 판단이 필요하다. 과도한 미끄러짐은 별도 이동 튜닝으로 다룬다.

키를 놓거나 유효 조건이 깨지면 그 플레이어의 진행률만 초기화한다. 피격 자체는 확보를 취소하지 않으며, 사망 또는 시선·거리 이탈로 중단한다. 중단 이유를 화면에 짧게 남긴다. 같은 화물에 여러 명이 접근하면 각자의 시간을 재되 속도를 합치지 않는다. 서버가 먼저 승인한 완료 한 건만 가치에 반영한다.

전송 화물은 슬롯을 차지하지 않는다. 서버가 완료를 확정하면 대상의 확보 상태와 팀 미정산 가치를 함께 바꾸고, 각 화면에서 전송 연출을 실행한다. 클라이언트 게이지가 먼저 끝나면 ‘전송 확인 중’으로 표시하며 점수를 미리 더하지 않는다.

### 중력 교란 화물

S01 전송과 동시에 해당 객차의 중력만 작전 종료까지 꺼진다. 연결 통로, 옆칸, 탈출 구역은 영향을 받지 않는다. 이미 확보 중인 다른 화물의 진행은 유지하되 이후 거리·시선 조건을 계속 검사한다. 화물과 선반은 고정하고 플레이어 이동만 바꾼다.

확보 전 설명은 ‘전송하면 이 객차의 중력이 꺼집니다’처럼 결과를 알려준다. 높은 선반의 화물은 사전 전환으로 얻는 이득이며, 바닥 화물을 먼저 챙길지는 팀의 선택이다. 이미 무중력인 영역에 재적용해도 중력과 보상이 중복 처리되지 않아야 한다.

### 상처와 스태미나

한 게이지 내부에서 영구 상처 `W`와 현재 스태미나 `S`를 구분한다. 최대치 `M = max(0, 100 - W)`이며 `0 ≤ S ≤ M`이다. 상처가 늘면 S를 새 최대치로 제한한다. **S가 0이면 걷기만 가능하고, W가 100이면 사망한다.** 달리기로 죽지 않는다.

시험값은 지상 걷기 450cm/s, 달리기 700cm/s, 달리기 소비 초당 20, 중단 0.75초 뒤 초당 25 회복이다. 상처가 없으면 연속 달리기 5초다. 일반 위험은 상처 20, 같은 위험의 연속 접촉 피해 간격은 1초다. 피격 직후 잠깐 위험 판정에서 벗어날 수 있어야 한다. 바닥 구멍과 선외 배출은 기본판의 주요 장치에서 제외하고, 추락 시 사망 판정만 준비한다.

사망하면 입력·진행 중 확보를 취소하고 팀원을 관전한다. 숨겨진 화물까지 포함해 소지품은 서버에서 떨어뜨린다. 전원이 사망하거나 연결된 생존자가 없으면 즉시 실패한다. 관전자의 핑과 장치 조작은 차단한다.

클라이언트 연결 종료자는 미탈출로 기록하고 진행 중 작업과 소지를 해제한다. 연결이 끊긴 플레이어는 정비 부활 대상에서 제외한다. 첫 프로토타입의 참가와 재참가는 Ready 상태에서만 허용한다. 호스트 종료는 Aborted로 구분하며 결과 가치를 지급하지 않는다.

### 정비 칸

5번 칸에 첫 생존자가 진입하면 30초 정비를 한 번 시작한다. 남은 임무 시간만 고정하고, 정비 타이머와 객차 위험은 실제 시간으로 진행한다. 후방의 팀원은 계속 확보할 수 있다. 이 효과는 전체 최대 30초이며 재진입으로 늘어나지 않는다.

정비 중 생존자가 부활 패널을 3초 조작하면 연결된 사망 팀원 전원을 안전한 스폰 위치에 부활시킨다. 각 플레이어는 이 정비에서 한 번만 부활하며 `W=50, S=50`으로 시작한다. 사망 당시 소지품은 원래 장소에 남는다. 생존자의 상처는 회복하지 않는다. 도구를 넣은 빌드라면 개인 보충 패널에서 잔량을 최대 2회로 한 번만 복구한다.

30초 만료 또는 생존자 한 명의 6번 칸 진입으로 정비를 닫고 임무 시간을 다시 진행한다. 정비 칸의 중간 탈출도 활성 중에만 시작할 수 있다. 일단 탈출을 시작하면 정비를 즉시 닫고 10초 출발 타이머와 임무 타이머를 진행한다. 한 명의 전진으로 정비가 끝나는 규칙과 남은 시간을 전원에게 표시한다. 테스트에서 합류 방해가 잦으면 수동 ‘정비 종료’ 방식과 비교한다.

정비 종료 시각과 부활·보충 완료 또는 중간 탈출 시작이 같으면 정비 종료를 먼저 처리한다. 진행 중 작업은 취소하고 소모나 부분 부활을 남기지 않는다. 종료 전에 승인된 출발은 계속 진행한다.

### 감시와 경보

기본판에는 회전 카메라 1대씩 사용한다. 거리 8m, 전체 시야각 60도, 노출 누적 1.5초, 시야를 벗어난 후 초당 50% 감소를 시작값으로 둔다. 엄폐물의 가림 판정을 서버에서 확인한다. 앉기 기능과 앉기별 수치는 초기 범위에서 제외한다.

의심이 가득 차면 1초 예고 후 감지 구역에 방어 펄스를 발생시킨다. 그 순간 범위 안에서 카메라와 시야가 연결된 플레이어만 상처 20을 받는다. 엄폐나 후퇴로 피할 수 있다. 카메라는 6초 재사용 대기 후 다시 감시한다. 범위·예고·재사용 상태를 색과 소리, 아이콘으로 함께 표시한다. 다음 객차나 탈출 안전 구역까지 공격하지 않는다.

이것은 **감시 발각의 결과를 정한 새 시험안**이다. 장시간 가만히 기다리는 벌칙을 줄이고 ‘위험을 감수하며 챙길지’ 관찰하려는 선택이며, 로봇 추격의 대체 검증이라고 주장하지 않는다.

### 탈출과 정산

기관실 또는 활성 정비 칸의 표시 구역 안에서 E를 1초 눌러 탈출을 확정한다. 실수 방지를 위한 시작 조작이며, 그 뒤 10초 동안은 누르고 있지 않아도 된다. 모든 생존자에게 출발 장소, 남은 초, 구역 안 인원/생존 인원을 표시한다. 시작 후 취소와 중복 시작은 불가하다.

출발 순간 서버가 살아 있는 플레이어의 캡슐 중심으로 구역 안팎을 판정한다. 적어도 한 명이 탑승했고 임무 시간이 남아 있어야 성공이다. 아무도 없으면 실패한다. 밖에 남은 생존자는 미탈출로 처리하고 플레이를 종료한다. 미탈출자 수는 보여주되 금전 벌칙은 넣지 않는다.

`최종 가치 = 팀 전송 가치 + 탈출자가 소지한 미각성 포드 가치`다. 기본판은 포드가 없으므로 팀 전송 가치만 정산한다. 실패 시 최종 가치는 0이지만 ‘전송했으나 정산하지 못한 가치’를 함께 표시한다. 서버는 RunId마다 결과를 한 번만 확정한다.

동시 사건은 서버의 판정 시각으로 정렬한다. 임무 마감 시각에 도달한 사건은 실패가 우선한다. 마감 전 같은 판정 시각에는 이미 유효했던 화물 완료를 반영하고, 피해·사망을 적용한 뒤 탈출 생존자를 판정한다. 이미 종료된 라운드의 지연 요청은 모두 무시한다. 이 순서는 획득·죽음·출발의 임의 Tick 순서에 맡기지 않고 테스트한다.

위험길은 이동만 약 8~12초, 안전길은 약 18~25초를 목표로 배치하되 측정 전 추정치다. 시간을 늘리기 위해 긴 복도를 덧붙이지 않는다. 화물의 위치와 접근 위험을 조정한다. 초당 가치만 높고 위험도 낮은 정답 화물만 남지 않게 한다.

격벽은 두 패널을 서로 다른 플레이어가 2초 동안 함께 유지하면 열린다. 원문의 1초 이내 시작 조건은 제외한다. 협동 시작 시각 맞추기보다 역할을 나누는 재미를 먼저 본다. 혼자 남아도 우회 콘솔로 전진할 수 있다.

탈출 구역 목표 면적은 4m×4m지만 기존 차량 유효 폭보다 넓다면 넓은 차량을 배정하거나 길이를 늘린 직사각형으로 바꾼다. 4명 캡슐 중심과 출발 패널 접근을 실제로 확인하고, 자료의 20m×5m×4m를 기존 메시의 실측값처럼 사용하지 않는다.

## 7 구현 구조

코드 위치는 `Source/SpacePirate/Prototype01/`, 콘텐츠는 `/Game/SpacePirate/Prototype01/`, 신규 맵은 `/Game/SpacePirate/Maps/Lvl_SPPrototype01`을 제안한다. 핵심 판정은 C++, 배치·표현·시험 데이터는 Blueprint와 DataAsset으로 관리한다. 다음 이름은 설계 후보이며 현재 구현되어 있는 클래스가 아니다.

| 역할 | 제안 요소 | 서버와 클라이언트의 책임 |
|---|---|---|
| 라운드 | `USP1RoundComponent`를 기존 Train GameState 계열에 부착 | 서버 상태·전송 가치·정비·종료 판정, 클라이언트 HUD 표시 |
| 시작과 참가자 | Prototype01 전용 GameMode/PlayerState | 준비·참가자 목록·죽음·관전·RunId 관리 |
| 확보 입력 | `USP1InteractionComponent`, 상호작용 인터페이스 | 소유 Pawn/Controller의 서버 RPC, 서버 재검사, 로컬 게이지 |
| 화물 | `ASP1TransferCargo`, `USP1CargoDefinition` | CargoId, 가치, 시간, Available/Transferred, 단일 완료 처리 |
| 객차 | `ASP1CarController`, 객차 데이터 | CarId, 컨셉, 위험 상태, 영역과 화물 식별 |
| 생존 | `USP1SurvivalComponent` | 서버 상처·죽음. 이동 컴포넌트와 달리기 제한·예측 연결 |
| 장치 | Laser, DualPanelGate, SecurityCamera, ExtractionZone | 서버 상태와 시각, 클라이언트의 예고·소리·문 애니메이션 |
| 기록 | 라운드 서버 로그 작성기 | 한 서버만 JSONL/CSV 출력. 클라이언트 중복 집계 금지 |

**Train GameState 통합 방식은 첫 단계에서 결정한다.** 기존 BP가 요구하는 부모·변수·함수를 유지한 채 라운드 컴포넌트를 붙이는 것이 우선이다. 새 C++ GameState 부모가 꼭 필요하면 모든 파생 BP와 배경 제어를 검증한다. 전송 점수만 필요한데 배경 전체를 다시 만드는 방향으로 확장하지 않는다.

상호작용 요청은 클라이언트가 소유한 Pawn/Controller 또는 그 복제 컴포넌트에서 서버로 전달한다. 월드 화물에 클라이언트 소유권을 번갈아 주어 RPC 문제를 해결하지 않는다. 소유권에 따른 RPC 실행 조건은 [Epic RPC 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine)를 따른다.

서버가 `AttemptId`, 시작 시각, 대상 ID를 관리한다. Start/Cancel 요청을 식별하고 오래된 취소가 새 시도를 지우지 않게 한다. 0.25초 정도의 가벼운 유지 신호와 0.75초 타임아웃을 시험값으로 두어 포커스 상실이나 연결 끊김 후 확보가 계속되지 않게 한다. 매 프레임 Reliable RPC를 보내지 않는다. 서버는 진행 중과 완료 시점의 조건을 재검사하고, 시계·가치·완료 여부를 클라이언트 입력에서 받아 확정하지 않는다.

공유 상태는 복제 속성으로 유지하고 연출 RPC만으로 기록하지 않는다. 임무와 장치 타이머는 서버 기준 시각으로 계산한다. 정비는 전역 Pause나 Time Dilation을 쓰지 않는다. GameMode의 서버 전용 규칙과 GameState의 공유 상태 구분은 [Epic GameMode와 GameState 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-mode-and-game-state-in-unreal-engine)를 참고한다.

레벨은 고정하고 배경만 움직인다. 10칸을 위해 World Partition 전환, 커스텀 엔진 수정, 새 범용 프레임워크를 먼저 도입하지 않는다. 기존 자산이 맞지 않는 부분은 작은 전용 시스템으로 보완한다.

## 9 제작 순서와 완료 조건

아래 공수는 기존 코드를 다룰 수 있는 UE 개발자 1명을 가정한 작업일 추정이다. 팀 인원과 숙련도에 따라 달라지며 일정 약속이 아니다. 아트 준비 3~5 작업일과 플레이테스터 일정은 별도다.

| 단계 | 작업 | 완료 조건 | 예상 작업일 |
|---|---|---|---:|
| P0 | 현재 BP 기본값·입력·GameState 확인, 복제 테스트 맵 준비 | 기존 열차·Pawn 연결 보존, 변경 범위와 기준 기록 | 0.5~1 |

| P3 | 협동 격벽·S01·카메라로 6칸 완성 | 2인·4인 진행 가능, 한 명만 남아도 탈출 경로 존재 | 3~4 |

| P5 | 최종 HUD·핑·최소 애셋과 소리·이벤트 기록 | 위험과 종료 이유를 설명 없이 이해, 로그와 정산 일치 | 2~3 |

합계 약 14~22 개발 작업일을 초기 계획으로 잡는다. P1을 마쳤을 때 실제 작업 속도로 다시 산정한다. **P3의 6칸에서 선택이 재미없다면 P4 콘텐츠 확장 전에 원인을 수정한다.** 12종 객차와 생성기를 추가해 문제를 덮지 않는다.

도구 시험안은 ‘차단기’ 하나다. 250cm 안의 레이저 제어부에 1초 조작하면 해당 장치만 6초 정지, 잔량 2회다. 완료된 성공 사용에만 차감하며 이미 정지된 장치를 연장하지 않는다. 동시 요청은 한 번만 적용한다. 카메라·탈출·중력·필수 격벽을 모두 여는 만능 도구로 확장하지 않는다.

## 10 테스트와 재미 판정

### 기술 완료 기준

기능을 추가할 때마다 Listen Server 1개와 Client 1개로 확인하고, 주요 단계 말에 4인으로 반복한다. 가능한 마지막 검증은 서로 다른 PC의 패키지 빌드로 수행한다. 로컬 4창 렌더링 속도를 한 사용자 PC의 성능으로 해석하지 않는다.

| 검사 | 기대 결과 |
|---|---|
| 두 사람이 같은 화물 완료 | 가치 1회 증가, 한 개의 CargoId만 완료 |
| E 놓기·화면 포커스 상실·거리/시선 이탈·벽 가림 | 서버에서 중단, 이유 표시, 새 시도는 0부터 |
| 완료 직전 사망·접속 종료 | 종료 규칙에 따라 일관된 결과, 진행이 남지 않음 |
| 중력 전환 중 확보·객차 경계 이동 | 서버와 클라이언트의 중력과 확보 상태 일치 |
| 한 생존자만 남은 격벽 | 12초 우회로 통과 가능 |
| 정비 재진입·동시 부활·앞칸 진입 | 정지/부활/보충 중복 없음, 팀에 종료 이유 표시 |
| 중간과 최종 탈출 동시 요청 | 먼저 승인된 한 출발만 존재 |
| 카운트다운 중 이탈·합류·전원 이탈 | 출발 순간 위치로 판정, 빈 탈출 실패 |
| 남은 9초에서 출발 시작, 마감과 출발 동시 | 실패하며 추가 10초를 얻지 못함 |
| 결과 중복 요청·늦은 확보 RPC | 정산 1회, 종료 뒤 가치 불변 |
| 재시작 5회 | 화물·문·중력·정비·상처·로그 RunId 초기화 |
| 호스트 종료 | 연결 중단으로 표시. 플레이 실패와 구분, 정산 없음 |

지연 검사는 정상 환경, 관측 RTT 약 100ms, 약 200ms와 손실 2% 조건을 순서대로 시험한다. 설정한 단방향 지연을 RTT라고 잘못 기록하지 말고 실제 `stat net` 수치를 남긴다. 값을 중복 적용하지 않는다. 단일 PC 기본 PIE는 지연·손실을 재현하지 못하므로 [Epic Network Emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine)의 설정 방법으로 검사한다. 극한 500ms/10%는 정산 중복·고착 탐지용 추가 시험이며 재미 평가 표본에 섞지 않는다.

### 남길 데이터

서버 로그에 RunId, 빌드 식별자, 설정 버전, 배치 A/B, 인원, 임무 제한시간을 기록한다. 이벤트는 CarEnter/Exit, AcquireStart/Cancel/Complete, HazardHit, GateOpen, GravityChange, MaintenanceStart/End, Revive, ExtractionStart, RunEnd를 남긴다. 각 이벤트에는 서버 시각, 플레이어 ID, CarId, CargoId, 취소·실패 이유를 필요에 따라 넣는다.

최종 팀 가치와 CargoId별 전송 가치 합계가 같아야 한다. 객차 체류는 플레이어별 체류와 팀의 첫 진입부터 마지막 이탈까지를 구분한다. 첫 이탈 때 남긴 가치와 판 종료까지 끝내 남긴 가치를 구분해 되돌아가기를 오판하지 않는다. 플레이 음성·발언을 기록할 경우 참가자에게 사전에 알리고 관찰 메모로도 대체할 수 있다.

### 테스트 진행

1. 개발 팀이 화물 무시 최단 통과, 선택 수집, 전량 회수를 각각 3회 수행한다. 불가능한 배치부터 수정한다.
2. 동일 배치에서 원안 600초와 시험 420초를 비교한다. 팀별 A/B와 B/A 순서를 번갈아 학습 효과를 줄인다.
3. 권장 표본은 개발에 참여하지 않은 4인 팀 3개가 각 3판, 총 9판이다. 별도로 2인 팀 2개가 각 2판을 한다. 모집이 어려우면 한 팀부터 시작하되 일반적인 재미를 입증했다고 표현하지 않는다.
4. 두 번째 세션에서 배치 B를 사용한다. 종류·총 가치·위험 강도는 유지하고 화물 위치와 위험길 방향만 바꾼다.
5. 인원별 결과는 따로 본다. 2인은 600초로 먼저 시험하고 통과성 확인 후 시간을 조정한다. 4인과 원점수를 직접 비교하지 않는다.

시간 튜닝은 `최단 통과 시간 + 탈출 10초 < 제한시간 < 숙련 팀의 전량 회수 후 출발까지 시간`을 만족하는 범위에서 시작한다. 여기서 시간은 정비로 정지한 시간을 뺀 임무 소비 시간이며, 최단 통과는 탈출 장치에 도달할 때까지다. 전량 회수 후 출발이 420초보다 짧으면 이동 거리부터 늘리지 말고 화물 접근 위치·고가치의 위험·동시 분담 가능성을 점검한다. 이후 시간을 30~60초 단위로 조정한다. 최소한 2개 이상의 합리적인 선택 경로가 남아야 한다.

### 채택과 수정 기준

아래 수치는 작은 표본에서 다음 결정을 내리기 위한 **가설 기준**이다. 통계적 유의성이나 흥행 예측을 뜻하지 않는다.

| 판단 항목 | 우선 목표 | 미달 시 먼저 바꿀 것 |
|---|---|---|
| 자발적 포기와 전진 | 학습 뒤 2·3판 중 2개 이상 객차에서 이유 있는 포기 관찰 | 전방 보상 표시, 안전/위험 보상 차이, 시간 예산 |

| 회수량 | 4인 학습 뒤 성공 판의 배치 가치 대비 대략 45~75% | 너무 높으면 욕심 비용, 너무 낮으면 접근·설명·장치 난도 |
| 종료 납득 | 12명 중 10명 이상이 실패/미탈출 이유를 정확히 설명 | 경고, 시각 경계, 카운트다운과 정산 표현 |
| 재도전 의향 | 12명 중 8명 이상이 조건 없이 한 판 더 하기를 선택 | 반복 대기·보행 비중, 개선 가능한 실패 원인 |

성공률은 첫 학습 판보다 반복 판에서 올라가는지 본다. 남긴 화물이 많아도 규칙을 몰랐거나 UI가 불편했으면 가설 1을 통과시키지 않는다. 강제 문 대기로 생긴 대화도 자발적 협동과 따로 기록한다. 재미가 약하면 변경 변수 하나를 정해 한 차례 더 시험하고, 여전히 선택이 생기지 않으면 기획안 1의 핵심 가설이 약하다고 기록한다.

## 11 후속 실험 순서

첫 추가 실험은 N01 포드 한 개다. 6번 이후 선택 공간에 가치 1,200, 최초/재획득 3초, 이동속도 0.9배, 인벤토리 1칸의 한 손 화물로 배치한다. 누적 실제 피해 50 또는 소지한 채 무중력 영역에 들어가면 각성한다. 피해 누적은 플레이어가 아니라 포드에 저장하며 숨겨진 슬롯도 소지로 판단한다. 직접 내려놓아도 누적값은 유지한다. 경고는 누적 30 이상 또는 무중력 경계 접근 시 한 번 표시한다. 새로운 가치 총액 8,260은 기본판과 구분해 기록한다.

기존 인벤토리에 도구가 이미 들어갔다면 빈 슬롯·잔량 보존·슬롯 변경을 검증한다. 운반 속도 배율이 숨긴 포드까지 중복 계산되는지도 확인한다. 이동 중 무중력 진입, 다른 사람에게 전달, 죽음, 내려놓기, 관전과 탈출에서 하나의 포드만 남아야 한다.

다음은 적재 칸 35초 하역, 제한적 절차 생성, 근접 음성과 청음의 순서로 검토한다. 하역을 켠 판과 끈 판은 별도 설정으로 기록해 전체 제한시간만으로 생기는 욕심과 구별한다. 생성기는 기존 차량 배열 편집과 다른 기능이다. 서버가 검증된 구성 결과를 만들고 클라이언트에 동일하게 전달하며, 실패 시 검증된 고정 편성으로 돌아간다.

기획안 2 제작 계획은 이 문서와 별도로 작성한다. 기획안 1의 포드·피해 규칙을 2번의 가방·체포에 자동 적용하지 않는다. 기획안 3은 양쪽 프로토타입 결과를 바탕으로 준비 효과 한 개를 연결하는 범위를 먼저 정한다.
